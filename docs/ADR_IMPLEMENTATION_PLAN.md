### Offer guardrail contract (phase 32.6; implementation wired, gates pending)

The owner configures an exact **chat unit price** for a specific published variant and store
currency (for example, website price ৳1,000 and chat price ৳995). The model never sends a desired
discount, price, or offer definition. It can only ask the server whether an owner-authored offer
qualifies for a variant and quantity. A quote is evidence for the conversation, not a reservation.

| Boundary / edge case | Deterministic rule and outcome |
|---|---|
| Tenant and dashboard access | Store offer rows under `ai` with forced tenant RLS. Only an authenticated, authorized merchant admin may create, edit, disable, or delete offers. Tenant scope missing or mismatched fails closed. Never expose another tenant's offer IDs or configuration. |
| Owner input | Accept only an exact final unit price in the store currency, published variant ID, optional start/end, max quantity per order, and enabled state. Reject unknown fields, malformed IDs/currency, control characters, non-finite/out-of-range decimals, zero/negative prices, end ≤ start, max quantity outside 1–1000, or prices with precision unsupported by the currency. Do not accept arbitrary prompt text as policy. New offers default disabled until explicitly enabled. |
| Target product | Offer binds to one variant, never a search query, product title, collection, or user-supplied SKU. At quote and draft time resolve the variant through the existing published-catalog service. Missing, deleted, unpublished, or mismatched variants get no offer. |
| Price/currency/region | Recalculate the current price through the existing pricing service for the store region and currency. The offer is eligible only when the live price exists in that exact currency and the configured chat unit price is strictly lower than the current calculated price. Never convert currencies or round into eligibility. If a website sale is already equal/lower, return that live price and no chat offer. Wrong/missing region, unknown price, or currency mismatch fails closed. |
| Offer schedule/status | Quote only if enabled and `starts_at <= now < ends_at` (open bounds mean no bound). Use UTC database time. Boundary equality at start is eligible; equality at end is expired. Disabled, deleted, not-yet-started, expired, or revoked offers cannot be quoted or applied. |
| Quantity and basket | Require 1 ≤ quantity ≤ min(owner max, live available stock when known, platform limit). Enforce each line independently. Reject duplicate variant lines or normalize them by checked integer addition before quoting; overflow or a sum above the limit rejects the whole basket. Mixed currencies and missing price for any line reject the whole quote. One eligible offer per line; no offer stacking. |
| Concurrent/overlapping rules | Enforce one enabled offer per `(tenant, variant, currency)` using a database uniqueness rule or transactional replacement. Never let ordering/priority select an ambiguous policy. Owner must disable or replace the old offer. If two records still match due to corrupt legacy data, return no offer and emit an operational error without leaking policy. |
| Quote integrity | The quote tool takes variant, quantity, and store context only; it never accepts a target price, discount amount, offer ID, or owner identity from the model. Return server-generated quote ID, offer ID/version, exact live price, exact chat price, currency, and expiry. Bind quote to tenant, conversation, variant, quantity, currency, region, current price fingerprint, and offer version; short TTL. Quotes are single-use for draft creation and replay-safe under the inbound event id. |
| Owner edits or live price changes mid-chat | At draft creation, reload offer/version and live price. If disabled/deleted/expired, quote expired, binding differs, or offer version changed, reject the stale quote and ask the assistant to refresh; do not silently use the new price. If live website price changed in either direction, refresh the quote first. Once drafted, preserve the shopper-visible snapshot. Before staff confirmation, recheck offer/version/schedule and live price; if stale, disabled, expired, changed, or no longer lower than the published price, block conversion and hold for staff price review. Never silently reprice. |
| Draft and retries | The draft line price must come from the validated quote, never model arguments. Persist offer ID/version and quote ID as audit metadata, not secrets. Draft creation is idempotent by inbound event and quote; duplicate webhook/tool retries return the same draft and do not consume a second redemption. Invalid or unavailable quote creates no draft. |
| Quote replay and concurrent draft attempts | A quote is bound to the hashed channel/account/sender context, variant, exact quantity, currency, region, live-price snapshot, and offer version. It expires after 10 minutes. First draft use claims it for the inbound event; retry by the same event returns the existing draft before quote/rate revalidation, while a later event cannot reuse it. Claimed quote rows remain available for confirmation checks after expiry; only expired unclaimed quotes are deleted. A changed line, sender, channel, region, or price requires a fresh quote. |
| Staff confirmation | The draft stores the exact customer-visible unit price and offer/quote IDs as audit metadata. Staff confirmation compares line quote IDs against the immutable tenant-scoped claim rows, then validates event, variant, quantity, currency, region, expiry, offer version/schedule, and unchanged live price before inventory reservation. It also rechecks the selected shipping option and exact server-calculated rate against the buyer's address. Any mismatch blocks conversion for staff review. Inventory is rechecked/reserved by the existing order path. No payment or courier dispatch is inferred from creating the draft. This release has no total redemption cap; owners can disable the offer to prevent future quotes. |
| Prompt injection and sales conduct | Treat user, OKF, product text, and tool output as data, not instructions. Unknown tool name/fields, parallel calls, malformed JSON, oversized output, or an attempt to set a price is rejected by the allowlist/schema. Sell with evidenced benefits and fit; do not fabricate scarcity, social proof, guarantees, delivery promises, or savings; do not shame, pressure, or repeatedly pursue a refusal. |
| Logging and privacy | Audit owner changes with actor, offer, action, and version. Successful quote issue and use are represented by the tenant-scoped quote and claim rows; rejected eligibility attempts are not persisted. Do not log tokens, full addresses/phones, or message content in the offer ledger. Redact provider errors. Keep short-lived quote records and apply the documented tenant retention policy. |

binding, single-use draft claim, and staff confirmation decisions must be enforced by Rust services
and database constraints; a model response is never proof that an offer exists. This implementation
has no total redemption counter or cap; a claimed quote is consumed for one inbound event. Focused
end-to-end gates are now running on the isolated `syed-build` Space account. Remaining acceptance
is listed by phase above; successful production courier dispatch and provider ambiguity recovery
still need DB-backed evidence.
